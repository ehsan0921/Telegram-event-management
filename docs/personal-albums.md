# Personal albums and photo likes

Personal albums reuse photo collections, Telegram upload and existing sharing controls. New personal albums start private; older collections keep their settings and links. Upload original files using Add files in Telegram. The + beside each photo saves that one photo into an owned album, or creates a private album and saves the photo immediately. There is no whole-album copy action.

New photo saves require valid server-side source access at commit time, within the existing state transaction. They snapshot the media fields using the same Telegram file ID; saving does not download or upload the photo bytes again. The saved media record thereafter follows destination access, so authorized destination viewers do not need source membership or a separate linking grant. Source link revocation closes future source access but does not recall previously saved copies. The picker and sharing controls explain this behavior. Source-hidden uploader attribution stays hidden in the saved record. Removing a saved item never deletes the original or other saved copies.

Existing source-dependent references retain their old access and policy epochs, receipt history and idempotency records. They are not silently converted to independent copies. Their viewers still need current source access, and disabling/re-enabling linking does not revive old foreign grants. A viewer may explicitly save a currently accessible referenced photo through the new single-photo path; the older reference remains unchanged. Removing a reference never deletes its source. Previously delivered/in-flight copies cannot be recalled.

Photo likes use authenticated user identity and canonical original identity; setting liked=true/false is idempotent. Authorized viewers see an outline/filled heart and a noninteractive count. The API returns only count and the current user's liked state, with no liker names, identities or list pagination. Stored likes remain intact. Owner-only access controls identify exact users, require confirmation and compare versions. Media-only blocks preserve event RSVPs, payments and other event features. Existing standalone sharing controls rotate old capability links. Event invitation tokens retain their existing invitation semantics.

No schema migration is required. Compatible event fields and media_likes/media_import business records use the existing records table. Import request tombstones survive removals and database snapshots. Never clear these records to retry a request. The tested feature rollback is ALBUM_SOCIAL_ENABLED=false on this privacy-aware Worker: it pauses new social writes and hides social controls while retaining reference authorization, revocation and all records. Keep existing variables/secrets when setting it. Do not restore/reset D1 or deploy pre-feature code after new access blocks/references exist; older code does not enforce these access rules. Use this safe mode and a forward fix instead.

Validation uses fictional SQLite/D1 fixtures, signed Mini App requests and mocked Telegram. It covers both serialized orders of save versus source revocation, destination access for previews/likes/status/sends, original preservation, single-photo scope, duplicate requests, removed-item tombstones, storage interruption, legacy-reference compatibility, receipt preservation and count-only like privacy. These checks do not establish physical iOS/Android or real Telegram client behavior.
